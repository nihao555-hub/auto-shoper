# Alibaba 批量上品体验优化计划

## 1. 文档信息

- 状态：计划功能已实施，待用户统一测试与线上草稿验证
- 适用范围：Alibaba 国际站批量上品工作台
- 目标分支：`devin/1783860981-fix-store-oauth-loop`
- 关联规范：[Alibaba 批量上品动态表单约定](./alibaba-listing-form-contract.md)
- 核心原则：AI 能安全完成的尽量自动完成；必须由人工提供的内容要做到一眼知道填什么、去哪里找、怎样才算正确。

## 2. 背景与问题

当前系统已经建立以下正确基础：

- 以 Alibaba 实时类目 Schema 作为字段事实源。
- 区分 AI 候选、商家事实、业务系统数据和店铺默认值。
- 禁止 AI 猜测价格、MOQ、库存、重量、包装、认证等经营事实。
- 在创建草稿和正式发布前执行后端来源校验与必填校验。
- 采用“上传图片 → 确认 AI 候选 → 补齐事实 → 创建草稿 → 回读发布”的五步流程。

目前主要问题不再是字段规则缺失，而是用户体验和责任状态还不够精细：

1. AI 确认主要使用商品级 `aiConfirmed`，无法表达单个字段已经确认、被修改或仍待确认。
2. “一键确认全部”会将多个 AI 字段同时提升为可信数据，缺少逐字段证据和变更记录。
3. 动态表单仍直接暴露较多 API 字段语言，用户需要先理解平台字段再填写。
4. 异步选项、父子联动和 `complex/multiComplex` 字段尚未形成完整控件体系。
5. 前端仍承担部分字段别名、默认值映射和请求拼装逻辑，可能与后端策略产生偏差。
6. 已完成字段、待确认字段、待填写字段和错误字段的任务优先级不够直观。

## 3. 产品定位

产品不应成为 Alibaba 原生表单的另一套皮肤，而应成为“上品任务转换器”：

> 系统自动完成可安全解决的字段，并把剩余平台表单转换成少量、简单、有证据、有示例的业务问题。

### 3.1 竞品做法的吸收

参考店小秘等跨境 ERP 的成熟做法：

- 商品采集与平台字段映射。
- 店铺模板和类目模板复用。
- 标题、描述、翻译和图片等 AI 辅助能力。
- SKU、价格、库存、包装等事实由商家或 ERP 提供。
- 发布前进行平台规则校验。

### 3.2 本项目的差异化

- 不直接把完整平台表单交给用户。
- 默认隐藏系统已经安全解决的字段。
- 用户只处理“请确认”“请填写”“需要修正”三类待办。
- 每个人工问题都提供来源提示、示例、单位和即时校验。
- 未识别字段始终由商家处理，不能默认分配给 AI。

## 4. 目标与非目标

### 4.1 本次优化目标

1. 将商品级确认升级为字段级可信状态。
2. 让用户默认只看到尚未解决的任务。
3. 将 Alibaba 字段翻译为自然语言业务问题。
4. 由后端统一输出字段责任、来源门禁和任务状态。
5. 完整支持 Schema 中常见输入类型、异步选项和复杂字段。
6. 在草稿创建后提供回读差异，形成发布闭环。
7. 为后续 ERP 导入、模板复用和批量填写建立稳定接口。

### 4.2 第一阶段非目标

- 不重做整个工作台视觉系统。
- 不接入新的第三方 ERP。
- 不建立通用低代码表单平台。
- 不让 AI 自动确认任何经营、供应链或合规事实。
- 不绕过 Alibaba 实时 Schema 或平台校验。
- 不在第一阶段扩展与上品无关的商品管理功能。

## 5. 目标用户流程

```mermaid
flowchart LR
    A["上传图片或导入商品"] --> B["AI 分析并建议叶子类目"]
    B --> C["获取实时 Schema"]
    C --> D["合并可信数据和店铺默认值"]
    D --> E["确认少量 AI 候选"]
    E --> F["回答未解决的业务问题"]
    F --> G["草稿预检和差异确认"]
    G --> H["创建草稿"]
    H --> I["回读 Alibaba 保存结果"]
    I --> J["用户显式确认发布"]
```

### 5.1 用户可见状态

| 状态 | 含义 | 默认呈现 | 用户动作 |
| --- | --- | --- | --- |
| AI 已完成 | 系统已安全解决或已有可信数据 | 折叠 | 可查看来源 |
| 请确认 | AI 已生成候选，但需要商家决定 | 展开 | 采用或修改 |
| 请填写 | 必须提供真实业务事实 | 展开 | 按引导填写 |
| 需要修正 | 本地或 Alibaba 校验失败 | 置顶 | 按错误提示修正 |

工作台默认开启“仅看待办”，已完成字段只在用户主动展开时展示。

## 6. 字段任务模型

后端应在现有 Schema Guidance 基础上输出统一的字段任务，前端不再自行组合责任规则。

```ts
type FieldTaskStatus = "completed" | "confirm" | "fill" | "invalid";

type FieldTask = {
  fieldPath: string;
  parentPath?: string;
  label: string;
  question: string;
  explanation?: string;
  example?: string;
  unit?: string;
  controlType: string;
  status: FieldTaskStatus;
  responsibility: "ai_candidate" | "merchant" | "business_system" | "store_default";
  allowedSources: FieldSource[];
  value: unknown;
  displayValueZh?: unknown;
  source?: FieldSource;
  confidence?: number;
  evidence?: string;
  required: boolean;
  blocking: boolean;
  validationErrors: string[];
  options?: SchemaOption[];
  asyncOptions?: boolean;
};
```

### 6.1 状态计算规则

- `completed`：字段有值、来源允许、无需确认且校验通过。
- `confirm`：来源为 `ai_generated` 或 `image_extracted`，或者字段明确要求商家确认。
- `fill`：字段必填、当前无可信值，并且责任属于商家或业务系统。
- `invalid`：字段有值但格式、选项、联动、来源或平台校验不通过。

状态必须由后端计算。前端只提交字段值和用户动作，不自行把 AI 数据升级为可信数据。

### 6.2 字段确认记录

字段级确认至少记录：

- 确认前的值和来源。
- 确认后的值。
- 用户是直接采用还是修改后采用。
- 确认时间和操作用户。
- 当时的 Schema 标识或版本信息。

商品级 `aiConfirmed` 在兼容期内可以保留为派生状态：只有所有阻断型 AI 候选均完成字段级确认时才为 `true`。

## 7. 傻瓜式填写设计

### 7.1 从字段名转换为业务问题

每个字段需要三层文案：

1. 主问题：用户需要做什么。
2. 来源提示：通常去哪里查找。
3. 正确示例：按什么格式填写。

示例：

| Alibaba 字段 | 主问题 | 来源提示 | 示例 |
| --- | --- | --- | --- |
| `FOBMinOrderQuantity` | 客户最少买多少件才能下单？ | 查看报价单或 ERP 的最小起订量 | `100 件` |
| `PackageSize` | 一箱货包装后的长、宽、高是多少？ | 查看装箱单或实际测量外箱 | `40 × 30 × 25 cm` |
| `GrossWeight` | 每箱货连包装一共多重？ | 查看装箱单中的毛重 | `12.5 kg` |
| `LeadTime` | 收到订单后多少天可以发货？ | 查看生产排期或现货承诺 | `7 天` |

优先维护高频语义字段的人工文案字典；未命中的字段使用 Schema 名称、提示和责任原因生成安全兜底文案。

### 7.2 页面结构

- 顶部摘要：已完成、待确认、待填写、错误数量。
- 默认过滤：仅看待办。
- 分组顺序：错误 → 类目 → AI 确认 → 交易/SKU → 包装履约 → 合规权利 → 其他字段。
- 每个任务卡只强调一个决策或一组强关联输入。
- 输入时即时校验，错误信息必须说明如何修正。
- 支持“我不知道怎么填”，展开来源说明和示例，不允许 AI 编造答案。

### 7.3 动态控件注册表

前端建立由 Schema 类型驱动的控件注册表：

| Schema 类型或语义 | 控件 |
| --- | --- |
| `input` | 单行文本或语义化数字输入 |
| `multiInput` | 多值编辑器，不使用原始换行文本作为最终体验 |
| `singleCheck` | 单选或下拉选择 |
| `multiCheck` | 多选列表 |
| 金额 | 金额与币种组合控件 |
| 尺寸 | 长 × 宽 × 高与单位组合控件 |
| 重量 | 数值与单位组合控件 |
| SKU | 可编辑规格表格 |
| `complex` | 嵌套字段组 |
| `multiComplex` | 可增加和删除的重复字段组 |
| 异步选项 | 父字段变化后加载 Alibaba 选项 |

## 8. 技术改造范围

### 8.1 后端

1. 扩展 Schema Guidance，输出 `FieldTask` 所需的展示和状态信息。
2. 将默认值合并、字段来源判断和状态计算集中到领域服务。
3. 提供字段级确认接口，禁止客户端直接把来源改为 `user_confirmed`。
4. 持久化字段来源、证据、确认和校验记录。
5. 增加异步选项查询和父子字段依赖描述。
6. 在准备草稿接口中返回标准化字段任务和阻断原因。
7. 创建草稿后保存回读结果，并生成本地值与平台值的差异。

### 8.2 前端

1. 将 `aiConfirmed` 从主状态降级为派生兼容状态。
2. 新增待办摘要、状态过滤和任务分组。
3. 将整体 AI 确认改为字段级采用、修改和拒绝。
4. 限制批量确认，只允许用户明确选中的低风险 AI 字段。
5. 用动态控件注册表替代当前通用输入框兜底。
6. 删除前端重复的责任判断、默认值识别和可信来源升级逻辑。
7. 增加草稿预检摘要和回读差异页面。

### 8.3 数据迁移与兼容

- 旧商品仅有 `aiConfirmed=true` 时，不自动生成字段级确认审计记录。
- 已发布历史数据保持只读展示。
- 未发布批次重新读取 Schema 后生成字段任务。
- 新旧接口并行一个发布周期，通过功能开关逐步切换。

## 9. 分阶段实施计划

### 阶段 P0：字段级可信状态与安全门禁

目标：解决确认粒度和前后端双重规则问题。

交付项：

- `FieldTask` 后端模型和接口。
- 字段级采用、修改、拒绝操作。
- 商品级确认状态改为派生值。
- 限制无差别“一键确认全部”。
- 后端统一来源升级和发布门禁。
- 关键来源策略单元测试。

完成标准：

- 任意未确认的阻断型 AI 字段都不能创建草稿。
- 前端无法自行伪造 `user_confirmed` 来源。
- 经营、供应链、合规字段无法通过 AI 确认入口提交。
- 未知字段稳定回退为商家填写。

### 阶段 P1：待办式补齐事实

目标：让用户只处理未解决问题，并且一眼知道如何填写。

交付项：

- 四状态任务摘要和“仅看待办”。
- 高频字段业务问题字典。
- 示例、单位、来源帮助和即时校验。
- 任务分组与错误置顶。
- 动态控件注册表基础版本。

完成标准：

- 已有可信值的字段默认不占用用户注意力。
- 所有待填字段均展示业务问题，而非只有 API 字段名。
- 数值、单位、单选、多选和多值字段可正确编辑。
- 用户能够从错误提示直接定位并完成修正。

### 阶段 P2：复杂 Schema 与效率能力

目标：覆盖真实类目中的复杂字段，并减少重复录入。

交付项：

- 异步选项和父子联动。
- `complex/multiComplex` 控件。
- SKU 表格。
- 批量填写及明确的应用范围。
- 类目模板和店铺默认值管理。
- Excel/ERP 数据导入接口预留或首个适配器。

完成标准：

- 选定试点类目的所有必填 Schema 类型均可完成填写。
- 批量操作不会影响未选商品或不允许继承的字段。
- 模板值仍需经过来源白名单和实时 Schema 校验。

### 阶段 P3：草稿回读与上线闭环

目标：降低平台保存差异和正式发布失败率。

交付项：

- 创建草稿前字段来源摘要。
- Alibaba 草稿回读。
- 本地值与平台保存值差异展示。
- 正式发布二次确认。
- 埋点、失败原因统计和运营看板。

完成标准：

- 平台转换、忽略或拒绝的字段可以被定位。
- 正式发布前必须完成回读和显式确认。
- 批量失败能够隔离到单个商品和具体字段。

## 10. 测试计划

### 10.1 后端契约测试

- AI 来源不能用于价格、MOQ、库存、重量、包装、认证等事实。
- `user_confirmed` 只能由确认接口生成。
- 店铺默认值只能用于白名单字段。
- 未知字段责任为商家。
- 复杂父字段可以由可信子字段满足，但不能被空对象绕过。
- Schema 变化后旧选项和旧值会重新校验。

### 10.2 前端组件测试

- 四种任务状态渲染正确。
- 采用、修改、拒绝操作只影响目标字段。
- 数字、单位、单选、多选、多值、异步和复杂控件正确提交。
- 切换商品和批次不会串值。
- 批量应用范围与界面提示一致。

### 10.3 端到端测试

至少选择三类商品：

1. 简单无 SKU 类目。
2. 多规格、多 SKU 类目。
3. 包含复杂属性或合规字段的类目。

每个类目覆盖：上传、AI 分析、字段确认、补齐事实、草稿预检、创建草稿、回读和发布前确认。

### 10.4 线上验证

- 先在演示模式验证界面和状态流。
- 再使用测试店铺或非正式发布批次创建草稿。
- 草稿回读无阻断差异后，才开放少量类目正式发布。
- 保留旧流程功能开关和回退能力。

## 11. 指标与验收目标

上线前先记录现有流程基线，随后按同类目、相近商品规模对比：

| 指标 | 说明 | 建议阶段目标 |
| --- | --- | --- |
| AI 安全完成率 | 无需人工填写的字段占比 | 持续提升，但不得降低来源合规性 |
| 平均人工字段数 | 每个商品实际需要填写的字段数 | 较基线降低 30% |
| 上传至草稿耗时 | 从导入到成功创建草稿的中位时间 | 较基线降低 30% |
| 首次校验通过率 | 第一次创建草稿即通过的商品占比 | 不低于 90% |
| AI 确认后修改率 | AI 候选确认后又被修改的比例 | 按字段统计并持续下降 |
| 发布失败率 | 正式发布阶段失败商品占比 | 较基线显著下降 |
| 错误定位率 | 能定位到具体字段的失败占比 | 100% |

效率指标不能覆盖安全指标。即使能够减少操作，也不能放宽经营事实和合规字段的来源门禁。

## 12. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| Alibaba Schema 随时变化 | 控件或字段映射失效 | 实时获取 Schema，缓存需带版本并在提交前复验 |
| 前后端规则并存 | 同一字段出现不同责任结论 | 后端输出最终任务状态，前端删除责任推断 |
| 批量操作误覆盖 | 多商品数据污染 | 显示作用范围、预览变更、保留字段修改记录 |
| AI 候选被过度信任 | 错误内容进入草稿 | 字段级确认、证据展示、来源门禁 |
| 复杂字段覆盖不足 | 特定类目无法发布 | 先选试点类目建立 Schema 样本和契约测试 |
| 历史数据缺少确认记录 | 审计链不完整 | 历史数据只读；未发布批次重新确认，不伪造记录 |

## 13. 推荐实施顺序

1. 先完成后端 `FieldTask` 和字段级确认接口。
2. 改造工作台右侧面板为四状态待办，不重做其他页面。
3. 将标题、描述、关键词、卖点和可见属性接入字段级确认。
4. 将价格、MOQ、库存、包装、交期和合规字段接入业务问题字典。
5. 补齐异步选项和复杂控件。
6. 收敛前端字段拼装与默认值映射。
7. 加入批量填写、模板复用和 ERP/Excel 导入。
8. 最后上线草稿回读、指标和分阶段发布。

## 14. 评审决策点

进入开发前需要产品、前端和后端共同确认：

- 字段级确认记录的持久化结构。
- 第一批试点类目和 Schema 样本。
- 高频业务问题字典的首批字段范围。
- 允许批量确认的 AI 字段白名单。
- 允许批量继承的事实字段及作用范围。
- 新旧流程功能开关和回退周期。

以上决策确定后，优先实施 P0。P0 是后续傻瓜式交互、批量能力和发布回读的共同基础。
